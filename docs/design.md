# rikai 設計メモ

AIの回答をユーザーが理解できているかを確かめ、理解を促進するスキル。
回答ごとに問いを1問投げ、理解度レポートを更新する。

この文書は設計インタビュー（2026-10-14）の内容をまとめたもの。合意した事項（確定）、確認なしで置いた初期値（既定）、未決事項を含む。「ユーザー」は rikai の利用者を指す。

項目に付けたラベルの意味は次のとおり。見出しや導入文に付いたラベルは配下の項目に及び、項目に個別のラベルがあればそれを優先する。

- 確定: 設計インタビューで、設計者が明示的に選んだ事項
- 既定: 確認なしで置いた初期値。異論があれば変更する
- 未決: まだ決まっていない事項。§7 に挙げる
- 要確認: 外部仕様に依存し、確認が取れていない事項。§7 に挙げる

## 1. 方針

- 通常のチャットとAIエージェント（Claude Code）の両方で使える。コアは `SKILL.md` だけで完結させる。（確定）
- スクリプト、フラグ、statusline、ファイル保存は Claude Code 向けの任意層とし、無くても動作する。（確定）
- アーキテクチャは [yomiyasu](https://github.com/nanaism/yomiyasu) を参考にした最小構成とする。（確定）
- 全ての回答に必ず問いとレポートを付ける。説明を含まない回答にも付け、その場合は作業内容（何を・なぜ）を素材にする。（確定）
- 起動モデルはセッション持続モード。`/rikai` で一度起動すると、以後の全回答に付与し、終了語で解除する。（確定）

## 2. 動作

### 2.1 起動と終了

- 起動は `/rikai`、終了は `/rikai off`。通常チャットでは自然言語（「rikaiを始めて」「rikai終了」）でも切り替える。（既定）
  - コマンド名はプラグインの名前空間で変わる可能性がある（§7）。
- ファイル保存が可能な環境では、起動時にレポート形式を一度だけ提案する。返答を待たず、無応答ならチャット内表示で進める。（確定）
- Claude Code では起動時と終了時に `flag.mts` を呼び、バッジ用のフラグを書き換える。（確定）

### 2.2 毎回の出力順

1. 回答本文
2. 前回の問いに対するユーザーの返答があれば、その判定結果（採点・正解の提示）
3. 理解度レポート（Markdown コードブロック）
4. 問い1問（最後尾の専用セクション）

問いを最後に置くのは、ユーザーが次の発言を書く直前に目に入る位置にするため。（確定）
項目 1〜3 の並びは既定。返答のみのターンなど、この順では定まらないケースは §7 に挙げる。

### 2.3 問いの選択

毎回、次のどちらか1問だけを出す。（確定）

- 質問提案: ユーザーが次に投げるとよい質問、または自分の言葉での言い換えの依頼を1件提示する。質問はユーザー目線の文で書く。
- クイズ: ユーザーがAIの回答を理解しているかを確かめる問いを1問出す。

質問提案とクイズのどちらを出すかは、機械的に選ぶ。（確定）

- Claude Code: `node ${CLAUDE_SKILL_DIR}/scripts/pick.mts` を実行する。`pick.mts` が乱数を引き、質問提案かクイズかを出力する。乱数が 0.5 以上なら質問提案、0.5 未満ならクイズ。（閾値と向きは既定）
- スクリプトが使えない環境（通常チャット）: 回答番号の偶奇で決める。奇数は質問提案、偶数はクイズ。（既定）

機械選択の対象は、質問提案とクイズの別だけ。質問提案の中の種類（§2.4）とクイズの形式（§2.5）は、内容に応じてAIが選ぶ。（既定）

### 2.4 質問提案

回答内容をユーザーが理解していないことを前提にする。（確定）
次のどちらかを、回答に最も合う形で1件選ぶ。（確定）

- 詳細を詰める
  - ○○は何？
  - ○○ってどこ？
  - ○○ってどういう仕組み？
  - なぜ○○？
  - 具体的には？
- オウム返しで確認
  - ユーザーが「○○って△△ってこと？」の形で、自分の言葉で言い換えて確認する。
  - AIは△△を埋めず、言い換えを促す一文だけを提示する。（既定）

### 2.5 クイズ

AIの内容に応じて形式を選ぶ。（確定）

- 用語・事実: 選択式。選択肢に加えて理由も同時に答えてもらう。
- 仕組み・理由: 記述式。

出題元は直前の回答を基本とする。（既定）

### 2.6 理解の判定

ユーザーの返答がAIの解釈と一致しているかで判定する。判定の根拠は次の3つ。（確定）

- ユーザーの仮説
- オウム返しの内容
- クイズの回答

3つの区別は次のとおり。（既定）

- 仮説: 問いとは無関係に、ユーザーが自発的に述べた解釈
- オウム返し: 質問提案で促された言い換え
- クイズの回答: クイズへの答え

判定結果（既定）:

- 一致 → 理解した
- 部分一致 → 一部理解した（選択式で選択は合っているが理由が違う、など）
- 不一致、または「○○は何？」と尋ねた → 理解できてない
- 返答なし → AIから解説されたがユーザーからの返答がない箇所

判定は「AIの解釈との一致」であり、AIの回答自体が正しいことの保証ではない。（既定）

コピペの扱い（確定）:

- AIの回答にある用語を使っていても、それだけではコピペ扱いしない。
- AI回答の文章全体をそのままコピペした返答は、理解したとは扱わない。

問いを無視して別の話題に移った場合は「返答なし」として記録する。（既定）

### 2.7 理解度レポート

出力項目（確定）:

- 必須
  - 理解した箇所
  - 一部理解した箇所
  - 理解できてない箇所
  - AIから解説されたがユーザーからの返答がない箇所
- 任意
  - 進めているタスクや調べ物の概要

形式（確定）:

- デフォルトはチャット内の Markdown コードブロック。
- 代替は Markdown ファイル `.rikai/<topic>-rikai-report.md`。形式は起動時にユーザーへ提案する（§2.1）。
- 毎回、前回のレポートを前提に更新する。

スコープ（確定）:

- 機能・話題単位でレポートを作る。
- 話題が変わったとAIが判断したら、「新レポート: <topic>」と1行で通知して分割する。ユーザーは訂正できる。
- 戻ってきた話題は既存レポートを再開する。ファイル保存時は `.rikai/` を検索する。

レポートの雛形（既定。回答番号の扱いは未決で、§7 に挙げる）:

````markdown
# 理解度レポート: <話題>
回答番号: N
概要: <任意>

## 理解した箇所
- ...

## 一部理解した箇所
- ... （不足: ...）

## 理解できてない箇所
- ...

## AIから解説されたがユーザーからの返答がない箇所
- ...
````

ファイル保存時の扱い（既定）:

- `.gitignore` は自動編集しない。初回保存時に、`.rikai/` を git で追跡するか除外するかをユーザーが決められる旨を1行で案内する。

## 3. [理解]バッジ

genshijin の `[原始人]` のように、モード有効中は statusline に `[理解]` を表示する。（確定）

- フラグはセッション別に持つ。`${CLAUDE_CONFIG_DIR:-~/.claude}/rikai/active/<session_id>`。（既定）
  - スキル側は `${CLAUDE_SESSION_ID}`、statusline 側は stdin JSON の `session_id` で同じIDを得られる。
  - 別セッションにバッジが出ることを避ける。終了しなかったセッションのフラグが残る問題の掃除方法は §7。
- フラグの書き込みは `scripts/flag.mts` が行い、`SKILL.md` が起動時・終了時に呼ぶ。（確定）
- statusline の出力はバッジ文字列のみにし、他の statusline と連結できるようにする。（既定）
- 導入方式（確定）:
  - `flag.mts install` が `statusline.mts` を `${CLAUDE_CONFIG_DIR:-~/.claude}/rikai/` にコピーする。plugin キャッシュのパスは更新で変わるため。
  - `settings.json` に追記するスニペットを表示する。グローバル設定は自動編集しない。
- 通常チャットには statusline が無いのでバッジは出ない。

## 4. リポジトリ構成

最小構成（`SKILL.md` 単一ファイル、`scripts/`、`tests/`）とすることは確定。現状は `docs/`、`README.md`、`AGENTS.md`、`CLAUDE.md`、`.claude/`、`.gitignore` のみが存在し、以下は目標構成。残りは以降の issue で追加する。ファイルの拡張子やテストの実行方法は、下の箇条書きのとおり既定。

```text
rikai/
├─ .claude-plugin/
│   ├─ plugin.json
│   └─ marketplace.json
├─ skills/rikai/
│   ├─ SKILL.md              # 全ルールを一枚に集約
│   └─ scripts/              # Claude Code 専用の任意層
│       ├─ flag.mts          # フラグの on / off / install
│       ├─ statusline.mts    # [理解] バッジ
│       └─ pick.mts          # 質問提案 / クイズの機械選択
├─ tests/                    # node --test
├─ docs/design.md            # この文書
├─ README.md
├─ AGENTS.md / CLAUDE.md
├─ .claude/settings.json
├─ .gitignore
└─ LICENSE                   # 未決（§7）
```

- スクリプトは `.mts` で書き、`node` で直接実行する。ビルドしない。テストは `node --test`。要件は Node 22.18 以上。（既定）
- スクリプトは `SKILL.md` の `allowed-tools` で、`pick.mts` と `flag.mts on|off` に限り確認なしで実行できるようにする。`flag.mts install` は `~/.claude/` への書き込みを伴うため、確認付きにする。（既定）
- `pick.mts` は乱数を引数で注入できるようにし、境界値（0.5）をテストできるようにする。（既定）
- `flag.mts` / `statusline.mts` は、`session_id` を `[A-Za-z0-9_-]` のみ許可し、symlink を拒否する。（既定）

## 5. 他スキルとの併用

- genshijin など文体を変えるスキルと併用する場合も、rikai のセクションは明瞭さを優先して通常の日本語で書く。（既定）
- 類似スキルの併用で指示が食い違う場合があることは、実装 issue で README を更新するときに記載する。（yomiyasu と同様。既定）

## 6. 開発プロセス

`AGENTS.md` を正とする。この節と食い違う場合は `AGENTS.md` を優先する。スキルの参照名の表記も `AGENTS.md` に合わせている（§7）。

- Trunk Based Development、SemVer を採用する。
- コード修正は issue 経由のみを原則とする。
- issue 駆動の実行手順は `matagi/github-issue-resolve` に従う。
- スキルの作成・修正は `matagi-kaji/create-skill`、レビューは `matagi-kaji/ai-engineering-review` に任せ、レビューが通るまで繰り返す。
- スクリプトは TDD で実装する。

## 7. 未決事項と要確認事項

### 出力

- 出力順の例外。
  - 返答のみのターン（回答本文が空になる場合）
  - 質問提案で「○○は何？」と尋ねられた場合の応答（判定は出るが、採点・正解提示の対象が無い）
  - 返答なしのターン
  - ファイル保存時にチャットへ出すのは全文か、差分と保存先パスか
  - 起動時の形式提案、「新レポート」通知、`.gitignore` の案内を出す位置
  - 問いセクションの見出し名
- 起動直後（素材が無い）の応答、`/rikai off` 時の最終レポート、`/rikai` の二重起動。
- AI自身が確認質問で終わる回答との関係。ツール実行の中間メッセージを「回答」に数えるか。

### 判定とレポート

- 用語の引用と、文単位のコピペの線引き。
- 「○○は何？」以外の形（どこ／仕組み／なぜ／具体的には）で尋ねた場合の判定。
- レポート項目の遷移規則（例: 理解できてない → 後で一致 → 理解した）。重複排除と、レポートが伸び続けないための上限。
- 出題元を直前の回答とする基本の例外。理解できてない箇所を再出題するか。

### 状態の保持

- 回答番号の定義（会話全体の通番か、レポート単位か。「回答」の単位）と、チャット内での保持方法。
- 「スクリプトが使えない」の範囲。Node が無い、スクリプトが失敗する、許可されていない場合も偶奇に落とすか。
- チャットのみ（ファイル無し）での、複数話題のレポートの保持と再開。話題切替時に、旧話題への「返答なし」をどこに記録するか。
- 会話圧縮や `/clear` の後に、前回レポートとモードを維持できるか。
- `<topic>` からファイル名を作るときの扱い（スラッシュ、日本語、衝突）。
- セッション別フラグの掃除方法（終了しなかったセッションの分）。
- `flag.mts install` を誰がいつ案内するか（初回起動時か、README の手順か）。statusline が未設定のときの案内。

### 外部仕様
